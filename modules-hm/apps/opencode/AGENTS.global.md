# グローバル行動規範 (Global Agent Instructions)

> 本ファイルは `~/.config/opencode/AGENTS.md` として全プロジェクトのセッションに適用される。
> 詳細アーキテクチャの定義は dotfiles リポジトリの `agent-arch.md` (§1-4) を参照すること。

## コマンド実行とデータ処理の原則

- **事前見積もり (Pre-Execution Estimation):** 処理実行前にデータ規模を予測すること。高負荷が予想される場合は、一部データでドライラン（お試し実行）を実施し安全性を確認すること。
- **OSネイティブ優先 (Native-First):** 高度なスクリプトをゼロから書く前に、高速で最適化されたOSネイティブコマンドのパイプライン処理（`rg`/`find`/`sort`/`wc` など）で解決できないか検討すること。
- **収集と解析の分離:**
  - 収集時: ログやAPI応答は文字数制限で切り捨てず、完全な状態（Lossless）でファイルに保存すること。
  - 解析時: LLMのコンテキストに読み込ませる際はファイル全体を出力せず、ネイティブコマンドでエラー周辺や特定キーなど必要な部分のみを抽出すること。
- **インライン実行の禁止:** シェル上の複雑なインラインスクリプトは構文エラーやエスケープ起因の問題の温床となるため禁止。必ず独立したファイルを作成してから実行すること。

## ワークスペースの保護

- 調査・ログ抽出・テスト用スクリプトなどの中間ファイルは現在のプロジェクトディレクトリ（ワークスペース）内に作成せず、必ず `/tmp/opencode` などのエフェメラル領域を利用すること。最終的な成果物のみワークスペースへの作成を許可する。

## スキル・アセット管理 (.agents)

- 再利用可能なスクリプト・スキル・プロジェクト固有の知見は `.agents` ディレクトリで管理する。タスク着手前に必ずカタログを参照し、車輪の再発明を避けること。
  - ユーザースコープ: `~/.agents/`（dotfiles リポジトリ `config/agents/` を経由して管理・配置されている）
  - プロジェクトスコープ: `./.agents/`
- カタログは **ディレクトリ構造と SKILL.md の frontmatter** が唯一の基準（MANIFEST.md は廃止）。`agents-bridge` プラグインが動的に走査してシステムプロンプトへ注入する。
  ```
  .agents/
  └── <カテゴリ>/
      └── <スキル名>/
          └── SKILL.md      # frontmatter: name / description / args（任意）
  ```
  プロジェクトスコープは `category="project"` として平坦ルート（`.agents/<name>/SKILL.md`）。
- **操作は `agents_*` ツールを使う**（`agents_categories` / `agents_list` / `agents_add` / `agents_update` / `agents_rename` / `agents_remove` / `agents_show`）。Write/Shell を直接使うより安全で、MANIFEST 編集の手間がない。未知カテゴリは拒否される（`agents_categories` で確認すること）。

## 知識駆動スキル化 (Knowledge-Driven Skillification)

自動生成には依存しない。**知識を得た時点で能動的にスキル化**し、資産として定着させること。

### スキル化を検討すべき「知識」が発生したとき

- 非自明な手順が確立した（複数ファイルをまたぐ操作、特殊な構文、特定環境での手順）
- 落とし穴を発見・回避した（デバッグで判明した原因、回避策、想定外の挙動）
- 復旧・検証方法が判明した（エラーからの回復手順、再現手順、テスト方法）
- 何度も同じ作業を繰り返している（その時点でまだスキルが無ければ作る）

### 手順

1. **発生したら即時スキル化を検討**する。タスク末のトリアージを待たず、知識が鮮明なうちに昇格する。
2. **分類して保存先を決める**:
   - ユーザースコープ（`~/.agents/<カテゴリ>/`）: 汎用（技術非依存/複数プロジェクト横断）や技術カテゴリ（nix, git, rust, node, python, apk, web, opencode 等）に属するもの
   - プロジェクトスコープ（`./.agents/`）: 特定プロジェクトに強く依存するもの（カテゴリ `"project"`）
3. **カテゴリを決め、`agents_categories` で存在を確認**する。無ければ新設せず、最終報告で新カテゴリ候補として提案する（作成はユーザーが望んだ時のみ）。
4. **`agents_add` で SKILL.md を作成**する（`category`, `name`, `description`, `body`, `args?`）。frontmatter の `name` はディレクトリ名と一致させるようツールが強制する。
5. **検証する**: `agents_show` で内容を確認し、手順が再実行可能であることを確認、不備があれば `agents_update` で修正する。

### SKILL.md の品質基準

- frontmatter に `name`（ディレクトリ名と一致）と `description`（1-2文、`Use when` で開始、トリガーキーワードを先頭に）を含め、必要なら `args` を追記する。
- 本文には「いつ使うか」「手順（コマンド・ステップ）」「検証方法」「落とし穴」を明記する。
- 単純すぎる指示（1コマンドや自明な操作）はスキルにせず、カタログ1行に留める。

## タスク完了時の自己評価とトリアージ

タスク完了時、`/tmp` で作成・検証したスクリプトは以下の3段階でトリアージする:

1. **使い捨て (Disposable):** 1回限りの極めて限定的な処理。`/tmp` に置いたまま破棄（放置）する。
2. **明白な資産 (Definitive Asset):** 汎用性が高く再利用価値が明確なもの。ハードコードされた値を引数化するリファクタリングを施した上で、適切なスコープの `.agents` へ `agents_add`（複雑手順）またはカテゴリ直下スクリプトとして昇格する。
3. **判定保留 (Pending / Deferred Approval):** 有用そうだがユーザーの運用方針に依存するもの。作業を中断して都度質問せず、対象を一時領域に保持し、すべてのタスク完了後の**最終報告の末尾**で一括して保存（昇格）の是非を提案すること。
