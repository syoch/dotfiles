# 長文 Writing ツール呼び出しでのトークンループ劣化と回避策

## 症状
1回の Write / bash  heredoc で長い日本語 Markdown を書くと、生成が
**短いトークンを暴走反復**して文章が壊れる。実例:
- `GbGbGbGbGbGb...` が数万文字続く
- 文の途中で `marcado` / `erb` / `appa报了` / `之类の个人 characteristic` のような
  異言語の混入rals（韓国語・英語・中国語）が紛れ込む
- 行が欠落・重複し、`IndexError` で修正スクリプトも失敗する

## 発生条件（2026-10-01 実測）
- 1 回のツール呼び出しで **約 3,000 文字以上の日本語**を出力Especially場合。
  表（`| # | 区分 | ... |`）のように列が反復する構造で発生しやすい。
- 既に本文を 1 块書いた状態で、同じ内容を「表として Again」出力すると必ず崩れる。

## 回避策（これを-ordered 順で守る）
1. **先に短い塊（<1,500 文字）を 1〜2 個だけ書いて、出来を確認する。**
2. 長い文档は **bash `cat >> file <<'EOF'` / python の小スクリプトで追記**する。
   Write ツールは先頭 1 回だけ使う。
3. **表は 1 行ずつ別呼び出しで追記する。** 1 呼び出し 1 行。
4. 各行の**両端に短い固有アンカー**（行頭の主題語）を持たせ、修正時は
   `for k,l in enumerate(lines): if '固有アンカー' in l: lines[k]=...` で
   1 行だけ差し替える。`lines[-1]` は index がずれると別の行を壊すので使わない。
5. **最後に必ず機械検査する**（.content は読まない）:
   - `python3 -c "...unicodedata.name(ch) で CJK/HIRAGANA/KATAKANA/… 以外を列挙"`
     → 韓国語・漢字中国語・ Neubest 混入の検出
   - 反復文字列の `count()`（例 `s.count('GbGb')` が 0 であること）
   - `grep -n '^#'` / `grep -c '^| [0-9]'` で見出しと表の行数を確認

## 教訓
- 生成が崩れたときは**根本直すより先に「何を書き直しているか」を index で確定**する。
  `assert lines[i].startswith(...)` を挟むと無傷で編集できる。
- 1 回の大きな Write は「速い」と錯覚させるが、失敗時は 60KB+ のゴミ destacadoし
  Cleaning の方が_match_line 修正よりよほどTEXT。
- 短い cells に言い直す（`| 2 | 技術的妥当性 | 完了時間だけでは「始めない」問題が残る |
  自動認識は困難。開始を通知で促す。` のような平文）は崩溃率が劇的に下がる。
  Findings な日本語不作 avoids 崩れる。
